# Data model

Decided on 2026-11-23. Items marked *proposal* are defaults chosen during design and can
still be changed.

Keys are English and stable; the UI translates them (de, en). MCP tools return keys,
not translated labels, because Home Assistant's MCP server passes no language
(`language="*"`).

### Purchase fields (`type = purchase`)

| Field | Type | Notes |
|---|---|---|
| `price_estimated`, `price_actual` | numeric(10,2), EUR | |
| `product_url`, `vendor` | text | |
| `warranty_until` | date | Reminder before expiry (*proposal*: 30 days) |
| `approval_state` | enum | `not_required`, `pending`, `approved`, `declined` |
| `approval_by/_at` | user, timestamp | |

Approval is required when `price_estimated` ≥ threshold (default **250 €**, set in the
integration options). The approver must be an adult or admin other than the requester.
The AI can never approve. While approval is `pending` or `declined`, the ticket cannot
move beyond `discussing`.

The approval moves the ticket (recorded like any status change, with a `reason`):

| Step | Status afterwards |
|---|---|
| Approval becomes required (on creation or a price change) | `discussing`, unless closed |
| Approved | `new` ("Offen", to do), if it was `discussing` or `rejected` |
| Declined | `rejected` ("Träum weiter"), unless closed |

These moves happen for whoever took the step, also when that person could not move the
ticket by hand. When the price drops below the threshold again, the status stays.

Invoices are attachments of kind `invoice`.

## Recurring tickets

A series is a template (type, title, description, urgency, hearts, assignees, area and
device, checklist texts, planned type fields: entities, estimated price, link, vendor,
contractor, phone, estimated cost) plus a rule. Every round is a normal ticket with
`series_id`, `created_via = recurrence`, the series owner as requester and the
user "Automation" as creator; its checklist starts unticked.

- Mode per series:
  - `after_completion`: next due date = day the round was closed + interval
    (days/weeks/months/years). Until then `next_due` is empty.
  - `fixed_calendar`: rounds fall on `anchor + n × interval`, the anchor being the first
    due date (month ends stay put: 31 Jan → 28 Feb → 31 Mar). `rrule` is unused.
- A round appears `lead_days` before its due date (default **7**). The server checks
  every 15 minutes and right after a change.
- At most one open round per series. A round that is still open when the next date
  comes into view holds the series back; missed calendar dates are skipped, no round
  is created overdue.
- Closing a round as "Träum weiter" skips that round only; the series goes on. Deleting
  an open round counts as closing it.
- A series can start from an existing ticket (it becomes the first round) or blank with
  a first due date (the first round appears with the lead time).
- Changes to a series affect future rounds only. Pausing stops new rounds; ending a
  series keeps its tickets.
- Adults manage every series. Children manage their own series without assignees and
  with the fields they may set on their own tickets. AI and automations do not manage
  series. Purchases above the threshold ask for approval in every round.

## Rules

- Changes arriving via MCP or the nightly run follow the AI rules, whoever logged in
  the MCP client. Users with role `ai_agent` follow them on every channel.
- New users synced from Home Assistant start as `admin` if they are Home Assistant
  administrators, otherwise as `child` (least privilege, *proposal*); an admin assigns
  the right role.
- `new` is shown as "Offen": agreed and to do, not started yet. New tickets start there.
- Statuses can move freely between `new` … `acceptance` for humans with the right role.
- `done`: only the requester (acceptance). *Proposal:* an admin may close in exceptional
  cases; this is recorded in the history.
- `rejected`: adults and admins.
- AI agent: create, comment, move up to `acceptance`; never `done`, never `rejected`,
  never delete; implementation only when `ai_implement_approved` is set.
- Child: create, comment, accept own tickets; no assigning, no deleting, no AI approvals,
  no purchase approvals.
- Deleting: admin only. Done tickets are kept.

## Access

MCP access for now only for Home Assistant admins (`/api/mcp/haushalttickets` requires
an administrator account). All household members use the Kanban card.
